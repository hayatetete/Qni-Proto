# Qni NotebookとQURI SDK連携のためのワークフロー分析

**文書種別**：調査報告書ドラフト（構造固定版）  
**版**：0.2  
**更新日**：2026年9月10日

## サマリー

QURI SDKは、Python上で量子回路、量子状態、演算子を定義し、量子アルゴリズムを組み立て、シミュレータや実機で実行するためのライブラリ群である。量子化学、変分アルゴリズム、回路変換、サンプリング、期待値計算に加え、Early-FTQC・FTQC向けのアルゴリズムや資源見積もりも扱う。QURI Parts、QURI Algo、QURI VMが、それぞれ部品の構築、アルゴリズムの組み立て、実行環境上での評価を担う。［[1](#ref-1)］［[2](#ref-2)］

本調査では、QURI SDKの公式資料に加え、量子ソフトウェアの不具合調査、開発者への質問・インタビュー、再現性研究、量子コード生成ベンチマーク、GitHub Issue、Q&A、技術記事、研究発表を確認した。**一般的な量子開発で報告された問題**と、**QURI SDKまたは周辺連携で直接確認できた事例**を分けて整理した。

一般調査で最も注意すべき点は、**Notebookのセルが正常終了し、グラフや数値が表示されても、計算が正しいとは限らない**ことである。実例として、初期状態やパラメータ順の取り違え、ビット列の読み順、補助量子ビットを戻し忘れるアンコンピューティング、回路変換が挙げられる。別の種類の問題として、ライブラリ更新後の非互換、再現に必要なコードや環境情報の不足、大規模回路を目視だけでは確認できないことも報告されている。［[7](#ref-7)］［[13](#ref-13)］［[15](#ref-15)］

QURI SDKの公式仕様には、これらと照合すべき入力・工程が存在する。ただし、QURI SDK利用者だけを対象にした大規模な不具合調査は未実施である。このため、一般調査で見つかった問題をそのまま「QURI SDKでも頻発している事実」とは扱わない。本資料では、直接事例のある問題と、再現実験で確かめる必要がある仮説を分け、次の調査へつなげる。

### 主な調査結果

| 結果 | 利用者に見える状況 | 本資料での扱い |
|---|---|---|
| 実行成功と計算の正しさは別である | セルにチェックが付き、グラフも出るが、初期状態やパラメータ順が違うため別の量を計算している | 量子開発者調査で確認［[7](#ref-7)］ |
| 古典側も主要な不具合発生元である | 回路は正しいが、Pythonの配列、設定、最適化ループ、結果集計が誤っている | 26人の回答者による平均推定では古典コード43.5%［[7](#ref-7)］ |
| 更新と依存関係が再実行を妨げる | 前回動いたNotebookが、SDKやPythonの更新後にライブラリ読込または実行で止まる | 開発者調査と再現性研究で確認［[7](#ref-7)］［[12](#ref-12)］ |
| 回路図だけでは確認しきれない | 小さい回路ではゲートを追えるが、量子ビット数や層が増えると見落とす | 開発者調査で確認［[7](#ref-7)］ |
| 論文再現はコード以外の不足でも失敗する | 依存版、入力データ、実機条件、実行手順がなく、同じ計算を始められない | 再現性研究で確認［[13](#ref-13)］［[14](#ref-14)］ |
| AI生成コードは実行テストと専門家確認が必要である | コードが生成されても、古いAPI、回路論理、観測量、実機の原因診断を誤る | 複数の評価・事例研究で確認［[22](#ref-22)］［[24](#ref-24)］［[31](#ref-31)］［[34](#ref-34)］ |
| QURI SDKにも照合すべき工程がある | 状態・演算子・パラメータ・回路変換・Sampler・Estimator・外部SDK連携が一続きになっている | 公式仕様から接点を確認。発生頻度は未確認［[1](#ref-1)］［[28](#ref-28)］ |

## 1. はじめに

> **この章の要点**  
> Qni Notebookの機能を先に決めるのではなく、QURI SDKを使う研究・学習の作業と、そこで起きる問題を事実から捉える。

### 1.1 背景

量子アルゴリズム研究では、数式を理解するだけでなく、量子状態や演算子を定義し、回路を作り、古典計算と組み合わせ、シミュレータまたは実機で結果を確かめる。論文を再現する場合は、さらに論文中の条件、補足資料、公開コード、使用したライブラリ、実行環境を読み合わせる。

QURI SDKは、これらの作業をモジュール化された部品として扱う。QURI Partsは回路・状態・演算子・Sampler・EstimatorとNISQ向けの部品などを提供し、QURI Algoは主にEarly-FTQC・FTQC向けのアルゴリズムを扱い、QURI VMはデバイス条件を含む評価を担う。［[1](#ref-1)］［[3](#ref-3)］［[28](#ref-28)］

したがって、Qni Notebookとの連携を考えるときも、回路表示だけを見るのでは不十分である。**入力条件、Python処理、回路変換、実行先、結果の読み方までを一つの作業として調べる必要がある。**

### 1.2 目的

本調査の目的は、次の二点である。

1. QURI SDKを利用する研究・学習の作業を、入力から結果確認まで整理する。
2. 量子ソフトウェア全般で報告された問題とQURI SDK上の工程を照合し、Qni Notebookを検討する前に実証すべき仮説を定める。

本資料の段階では、機能案の選定や優先順位付けを行わない。既に実装済みのQni Notebook機能へ結論を寄せることもしない。

### 1.3 調査上の問い

- **問い1**：QURI SDK利用者は、どのような入力を用意し、どの順序で処理し、何を結果として確認するのか。
- **問い2**：量子ソフトウェア開発では、どの工程で、どのような問題が実際に報告されているか。
- **問い3**：そのうち、QURI SDKまたは周辺連携で直接確認できる問題は何か。
- **問い4**：直接確認できていない問題を、どのような再現実験で確かめるべきか。

### 1.4 調査の範囲

AIによる量子コード生成と論文再現は調査対象に含めるが、それだけに限定しない。手作業での実装、量子化学の設定、変分計算、回路変換、シミュレータ・実機実行、Early-FTQC・FTQC向けの作業も対象とする。

## 2. 調査方法

> **この章の要点**  
> 公式仕様、複数事例を扱う研究、個別事例を役割別に使い分ける。個別の投稿だけから発生頻度を推定しない。

### 2.1 調査した情報

情報は2026年9月10日までを対象にした。

| 情報源 | 調査で確認する内容 | 読み取り上の制限 |
|---|---|---|
| QURI SDK公式ドキュメント・公式リポジトリ | 構成、入力、処理、対応SDK、更新内容 | 利用者がどこで困るか、発生頻度までは分からない |
| 査読済み論文 | 複数プロジェクト・複数利用者にまたがる傾向 | QURI SDKだけの結果とは限らない |
| プレプリント | 直近の再現性調査、AI利用、シミュレータ不具合 | 査読前であり、結果が更新される可能性がある |
| GitHub Issue・Q&A | 問題が起きた状況、コード、出力、修正内容 | 1件から一般的な発生率は判断できない |
| 個人・プロジェクトの技術記事 | 作業中に起きた具体的な失敗と確認方法 | その環境・実験に限られる |
| 発表動画 | 論文の説明と文脈 | 数値は元論文で確認し、動画だけの主張は採用しない |

YouTubeでは、Paltenghiらによる223件の不具合調査を説明したACM SIGPLANの発表を確認した。本文の数値は動画ではなく元論文を参照した。［[8](#ref-8)］［[27](#ref-27)］

Xも検索したが、QURI SDKの問題を再現手順や環境情報とともに追跡できる投稿は確認できなかった。削除・編集され得る短文投稿を、件数を増やすためだけに採用していない。

### 2.2 事実と仮説の区別

本資料では、記述を次の三段階に分ける。

| 表示 | 意味 |
|---|---|
| **QURIで直接事例あり** | QURI SDK本体、QURI関連パッケージ、またはQURI利用記録に具体例がある |
| **一般研究で確認・QURI仕様に接点あり** | 他SDKを含む研究で問題が確認され、QURI SDKにも対応する入力や工程がある |
| **検証仮説** | QURI SDK利用時にも起こり得るが、今回の調査では直接事例または頻度を確認できていない |

### 2.3 本調査の限界

- QURI SDK利用者だけを対象にした大規模な質問調査は未実施及び確認できなかった。
- GitHub Issueや個人記事は、問題の存在を示すが、利用者全体での多さを示さない。
- 2026年の再現性・AI・シミュレータ研究には査読前の資料が含まれる。
- ベンチマークの点数は、使用モデル、プロンプト、テスト、SDK版によって変わる。異なる研究の点数を単純比較しない。
- 本資料は文献と公開記録の分析であり、QURI SDKを使った10件規模の再現実験はまだ実施していない。

## 3. 調査結果：量子ソフトウェア開発で報告されている問題

> **この章の要点**  
> 問題は回路だけでなく、Python処理、入力条件、依存関係、回路変換、実行先、結果の読み方にも生じる。特に、例外を出さない誤結果は「実行できた」という確認だけでは見つからない。

### 3.1 開発者調査から見える全体像

Zappinらは、大学・企業の量子ソフトウェア開発者26人への質問調査と、4人への追加インタビューを行った。26人中13人が、**クラッシュせずに誤った出力を返す問題**へ頻繁または非常に頻繁に遭遇すると答えた。これは、Notebook上ではセルが正常終了し、数値やグラフも表示されるが、内容が間違っている状況である。［[7](#ref-7)］

同調査で回答者が見積もった不具合の発生元は、平均で古典コード43.5%、量子固有34.0%、両者の境界19.0%、その他3.5%だった。古典コードには、たとえばPythonの配列処理、設定、入出力、古典最適化、結果の集計が含まれる。量子固有の例には、ゲート、初期状態、回路設計、測定、雑音がある。両者の境界には、古典のパラメータを量子回路へ渡す部分や、測定結果を古典側で解釈する部分が含まれる。［[7](#ref-7)］

### 3.3 「動いたが間違っている」問題の具体像

#### 3.3.1 初期状態またはパラメータが違う

開発者調査では、初期状態の準備間違いと、パラメータ配列の形・順番の間違いによって、誤解を招く出力になった例が報告された。［[7](#ref-7)］

Notebookでは、次のすべてが成功して見える可能性がある。

- Pythonの文法チェックを通る。
- セルが例外なく終了する。
- 回路図が表示される。
- シミュレータが数値を返す。
- 最適化履歴のグラフが描かれる。

それでも、パラメータθ0とθ1を逆に渡した、または期待した初期状態を作っていなければ、**実行した計算と調べたい計算が一致しない。**

#### 3.3.2 ビット列の表示規則が違う

Q&Aでは、利用者が`10`を期待したのに`01`が返り、回路が間違っていると考えた。原因は、Qiskitがビット列の右端へ番号の小さいビットを書く表示規則だった。［[17](#ref-17)］

ここで間違っていたのは量子状態ではなく、**量子ビット番号と表示文字列の対応の読み方**である。SDKをまたぐと、同じ状態でも表示が異なる場合がある。

#### 3.3.3 アンコンピューティングを忘れる

アンコンピューティングは、途中計算に使った補助量子ビットへ逆操作を行い、元の状態へ戻すことである。

```text
途中計算 → 必要な処理 → 途中計算の逆操作
```

逆操作を入れない場合もPythonは動く。しかし、補助量子ビットと出力がもつれたまま残ると、後の量子干渉が変わり、期待した出力にならない。Unqompの論文は、手作業でのアンコンピューティングを煩雑で誤りやすい作業として扱う。Q&Aには、逆操作の追加前は期待した干渉が起きず、追加後に期待状態へ戻る三量子ビットの例がある。［[15](#ref-15)］［[16](#ref-16)］

QURI SDK利用者がこの問題へ遭遇する頻度は、今回の調査では確認できていない。

#### 3.3.4 回路変換で「意味」と「見え方」を区別する

トランスパイラは、回路を実行先のゲート集合や量子ビット接続へ合わせて変換する処理である。QURI Partsも複数の変換を提供し、QiskitやTKETを利用する変換では数値誤差を伴う等価変換があると説明している。［[6](#ref-6)］

変換後の違いには、少なくとも二種類ある。

- **意味が変わった不具合**：Qiskit Issue #13079では、最適化が必要なCXゲートを削除し、変換前後の状態が一致しなかった。［[18](#ref-18)］
- **意味は同じだが並びが変わった状態**：Issue #5839では、SWAPと配置変更で中間状態の量子ビット順が変わったが、対応を補正した最終測定は一致した。［[19](#ref-19)］

したがって、回路図や状態ベクトルの配列が違うだけでは、誤りか正しい変換かを判断できない。

### 3.4 現在使われている確認方法

Zappinらの26人調査で報告された方法を整理する。人数は複数選択または自由記述を含む。［[7](#ref-7)］

| 確認方法 | 調査結果 | 確認できている限界 |
|---|---|---|
| 単体テスト | 88%が使用 | 単体テストだけで量子計算の意味をどこまで確認できるかは測っていない |
| `print`と回路の目視 | 専用テストツールを使わない16人中15人が使用 | 大規模回路や確率分布では追いきれない |
| 手作業のコード確認 | 自由記述11件 | 参照実装と量子・実機の知識に依存する |
| シミュレータ | 自由記述6件 | 実機と同じ雑音を再現できるとは限らず、シミュレータ自体にも不具合がある［[25](#ref-25)］ |
| 入力を変えて試す | 自由記述5件 | 有効性は同調査で測定されていない |
| 以前動いた版へ戻す | 自由記述3件 | 原因を特定せず回避している場合がある |
| 最小例へ縮める | 自由記述3件 | 有効性は同調査で測定されていない |
| 専用デバッグツール | 18人が使用していない | 認知不足、導入の難しさ、既存作業との連携不足が指摘された |

### 3.5 コミュニティの質問から確認できる問題

個別の投稿を並べるだけでなく、多数のQ&AやIssueをまとめた研究も確認した。

| 調査 | 対象 | 確認された内容 |
|---|---|---|
| Stack ExchangeとGitHub Issueの分析 | 量子ソフトウェアに関する投稿とIssue | 背後にある理論の説明、出力の解釈、古典計算と量子計算の知識差を埋めることが難所として報告された［[9](#ref-9)］ |
| 量子プログラミング言語利用者調査 | 251人 | 60.6%が公式文書から学び、42.8%が研究に利用。文書と使用例の不足が主要な問題として報告された［[10](#ref-10)］ |
| 4つのQ&Aサイトの分析 | 6,935投稿 | 理論・数学、アルゴリズム・応用、実験・ソフトウェア開発、教育・コミュニティに問題を分類。パラメータ制御は解決が難しい話題の一つだった［[26](#ref-26)］ |
| Bugs4Q | GitHub、Stack Overflow、Quantum Computing Stack Exchange由来のQiskit不具合 | 実在する42件を手作業で確認し、再現テストとともに収録した［[11](#ref-11)］ |

これらの結果は、利用者が求める説明がAPI名だけでは足りないことを示す。**理論上の目的、入力条件、出力の意味、実行結果を一緒に説明できなければ、コードが動いても判断は終わらない。**

### 3.6 論文再現でコード以外に不足するもの

「コードがない」という一言だけでは、再現できない状況を説明しきれない。実際には、次の情報が組み合わさって必要になる。

- Python、量子SDK、依存ライブラリの版。
- 入力データ、乱数、初期値、停止条件。
- 回路変換と量子ビット配置の条件。
- ショット数、雑音軽減、結果集計の方法。
- 実機名、実行日時、校正状態。
- 論文中のどの数値・図を、どの許容差で再現するか。

2026年の査読前研究`Works on My QPU`は、手作業で確認した量子計算論文127件のうち、コードを公開していたものは24.4%だったと報告する。さらに、公開コードの64.5%は新しく用意した環境で実行に失敗した。これはQURI SDKだけの調査ではなく、査読前の結果である。［[13](#ref-13)］

別の2026年プレプリントは、Bugs4Qの37成果物をQiskit 21版で計77,700回実行した。報告された再現率はQiskit 0.20.1で62.2%、2.3.1で16.2%であり、失敗の93.6%を依存関係に関連づけた。これもQURI SDKの数値ではないが、**コードだけを保存しても、環境が変わると同じ不具合や結果を再現できない**ことを示す。［[12](#ref-12)］

## 4. 調査結果：QURI SDKの作業構造

> **この章の要点**  
> QURI SDKでは、問題設定、量子オブジェクト、アルゴリズム、回路変換・実行、結果確認が別部品としてつながる。各部品への入力と、部品間の受け渡しが確認対象になる。

### 4.1 QURI SDKの構成

QURI SDKは、複数のライブラリをまとめたメタパッケージである。公式リポジトリは、主な構成を次のように説明している。［[1](#ref-1)］［[28](#ref-28)］

| 構成 | 主な役割 |
|---|---|
| QURI Parts | 回路、状態、演算子、Sampler、Estimator、雑音、トランスパイラ、外部SDKとの変換 |
| QURI Algo | 主にEarly-FTQC・FTQC向けのアルゴリズム部品、問題、目的関数 |
| QURI VM | デバイス条件を含むシミュレーション、回路実行、資源分析 |

QURI Partsは、Qulacs、Stim、ITensor、Qiskit、Cirq、Amazon Braket、Quantinuum、IonQなどのシミュレータ・SDK・サービスと接続するパッケージを持つ。量子化学ではPySCFやOpenFermionとの連携も用いる。［[28](#ref-28)］

### 4.2 代表的な作業の流れ

![QURI SDKを使う量子アルゴリズム研究の作業フロー](image/quri-sdk-workflow.svg)

> **図2の読み方**  
> 上段はQURI SDK公式資料から整理した代表的な工程である。下段は一般調査で確認した問題との照合点であり、「QURI SDKで頻発している」と示す図ではない。

| 作業 | 主に使うもの | 人が指定する内容 | 主な出力 |
|---|---|---|---|
| 回路と状態を作る | QURI Parts | 量子ビット数、ゲート、初期状態、測定 | 回路、状態、測定結果 |
| 期待値を計算する | QURI Parts | 演算子、状態、Estimator、雑音条件 | 期待値と推定誤差 |
| サンプリングで推定する | QURI Parts | 総ショット数、測定項のまとめ方、ショット配分 | 標本から計算した期待値と標準誤差 |
| 変分アルゴリズムを動かす | QURI Parts | 試行回路、初期パラメータ、最適化法、停止条件 | 更新履歴と最終結果 |
| 量子化学の問題を作る | QURI Partsと外部ライブラリ | 分子構造、電荷、スピン、基底関数、活性空間、写像 | 量子ビット上のハミルトニアン |
| 実行先へ合わせて変換する | QURI Parts / QURI VM | ゲート集合、量子ビット接続、最適化条件 | 実行先向けの回路 |
| シミュレータ・実機で実行する | QURI Parts / 各種バックエンド | 実行先、ショット数、雑音、認証情報 | 測定結果 |
| Early-FTQC・FTQC向けに評価する | QURI Algo / QURI VM | アーキテクチャ、デバイス条件、誤り率 | ゲート数、回路深さ、推定資源 |

### 4.3 結果を変え得る入力

QURI SDK公式チュートリアルから、同じ「実行」でも結果を左右する入力が複数あることを確認できる。

- **量子化学**：分子構造、電荷、スピン、基底関数、活性空間、電子数、Jordan–Wignerなどの写像。［[4](#ref-4)］
- **サンプリング**：総ショット数、測定項のまとめ方、ショット配分。［[5](#ref-5)］
- **回路変換**：実行先のゲート集合、量子ビット接続、変換の順序。［[6](#ref-6)］
- **変分計算**：試行回路、初期パラメータ、Estimator、古典最適化法、停止条件。［[2](#ref-2)］
- **実行先**：シミュレータ、実機、雑音モデル、バックエンド固有の設定。［[28](#ref-28)］

このため、最終値だけを見ても、違いの原因が分子条件、回路、変換、測定、後処理のどこにあるか分からない場合がある。

### 4.4 QURI SDKまたは周辺で直接確認できた事例

| 事例 | 実際に確認できる内容 | 言えないこと |
|---|---|---|
| QURI SDK公式リリース | v0.24.1には多重制御の補助処理における量子ビット数の誤りとキャッシュ修正、v0.26.4にはチュートリアルNotebookの量子ビット数不一致の修正が記録されている［[29](#ref-29)］ | 利用者が遭遇する頻度や影響の大きさ |
| Quantum Algorithm Grand Challenge（QAGC）2024公式環境 | QURI Parts 0.16.1、Qiskit 0.41.1、Cirq 1.1.0、NumPy 1.23.5などを固定し、別版を使う場合は版を申告するよう求めている［[30](#ref-30)］ | 固定しなければ必ず失敗すること |
| `quri-parts-oqtopus` Issue #39 | Qiskitとの同時利用時、終了処理で例外が出る再現例がある。報告者は計算結果への影響はないとしている［[20](#ref-20)］ | QURI SDK本体全体の互換性や発生率 |
| QURI Parts導入記事 | Apple M1・Python 3.13.1環境でRust、CMake、Boostが必要になった個人体験がある［[21](#ref-21)］ | 他OS・他Python版でも同じ問題が起きること |

ここから直接言えるのは、**QURI SDKにも版、依存関係、量子ビット数、外部SDK連携を確認すべき具体例がある**という範囲である。一般研究で報告された全問題がQURI SDKでも起きている、または多いとはまだ言えない。

## 5. 考察：一般調査とQURI SDKの照合

> **この章の要点**  
> 一般研究の問題とQURI SDKの工程には対応関係がある。ただし、対応関係は発生事実ではない。直接事例のない項目は、次の再現実験で検証する仮説として扱う。

### 5.1 照合の考え方

照合は、次の順で行った。

1. 一般研究から、実際に報告された問題を抽出する。
2. QURI SDK公式資料から、その問題に関係する入力・処理・出力を探す。
3. QURI SDKまたは周辺パッケージの直接事例があるか確認する。
4. 直接事例がなければ、QURI SDKでの発生を事実とは書かず、検証仮説に置く。

### 5.2 照合結果と検証仮説

| 仮説 | 一般研究で確認された問題 | QURI SDK上の接点 | QURIでの証拠 | 現時点の判断 |
|---|---|---|---|---|
| 仮説1 | 更新・依存関係で以前のコードが動かない | メタパッケージ、外部SDK、シミュレータ、量子化学ライブラリ | 公式リリース、版固定環境、導入記事、周辺Issueがある［[20](#ref-20)］［[21](#ref-21)］［[29](#ref-29)］［[30](#ref-30)］ | **QURIで直接事例あり**。ただし頻度は不明 |
| 仮説2 | 古典コードや古典・量子間の受け渡しで誤る | パラメータ更新、古典最適化処理、Estimator、結果集計 | QURI利用者の具体例は未収集 | **検証仮説**。小さな既知解で確認する |

| 仮説6 | 統計的な揺れ、雑音、コード不具合を区別しにくい | Sampler、Estimator、ショット配分、雑音モデル、実機 | 統計誤差の仕様は公式資料で確認。利用者がどこで誤判断するかは不明［[5](#ref-5)］ | **検証仮説**。理想・有限ショット・雑音ありを分けて比較する |
| 仮説7 | 論文のコードだけでは同じ結果を再現できない | QURI版、外部依存、入力条件、バックエンド、変換条件 | QAGCは版を固定しているが、QURI論文群の再現率は未調査［[30](#ref-30)］ | **検証仮説**。複数論文を新規環境で再実行する |
| 仮説8 | AIが構文上正しいが意味の違うコードを生成する | QURI PartsのAPI、状態・演算子・回路・Estimatorの組み合わせ | QURI SDKに限定したベンチマークは未確認 | **検証仮説**。同一課題を人手とAIで実装し、同じ判定基準で調べる |

- NISQ、量子化学、Early-FTQC、FTQCで問題の種類がどう変わるか。
- 初学者と研究者で、間違える工程や確認方法がどう違うか。
- 現在のQni Notebook機能が、どの問題を実際に発見できるか。
- どの問題を製品機能で扱い、どの問題を文書・テスト・教育で扱うべきか。

## 6. 追加調査：AIを使う場合の問題

> **この章の要点**  
> AIは量子コードを生成・修正できるが、評価条件によって成功率が大きく変わる。実行結果やテストを返すと改善する一方、論文から実機までの事例では専門家が科学的な誤りを発見している。

### 6.1 量子コード生成・修正の評価

各研究は別の課題を測っている。同じ表に置いても、点数を横並びで順位付けしない。

| 研究 | 何を評価したか | 主な結果 | 分かること | 分からないこと |
|---|---|---|---|---|
| Qiskit HumanEval | Qiskitコードを作る100件超の手作業課題。各課題に参照解、テスト、難易度がある | 実行可能な量子コードをテストで評価する基盤を提示［[33](#ref-33)］ | 文章の自然さではなく、実行テストが必要 | 論文全体の解釈やQURI SDKでの性能 |
| QuanBench | 44件の量子コード生成課題 | 総合正解率40%未満。古いAPI、回路構築、アルゴリズム論理の誤りを報告［[22](#ref-22)］ | 構文が通るだけでは不十分 | 論文からコードを作る一連の作業 |
| QCircuitBench | 25種類のアルゴリズムを、回路実行と古典後処理まで評価 | 存在しない制約の補完、ビット・ゲート位置の数え間違いなどを報告［[23](#ref-23)］ | 回路と後処理を一緒に評価する必要 | QURI SDK利用者の実作業 |
| QCoder Benchmark | プログラミング大会由来の課題を、Python実行だけでなくシミュレータの指標も使って評価 | GPT-4oは18.97%、推論モデルo3は最大78%。モデルと評価方法で差が大きい［[31](#ref-31)］ | シミュレータ固有の結果を評価へ含められる | 論文理解、QURI SDK、最新モデル全般への一般化 |
| QuanBench+ | Qiskit、Cirq、PennyLaneで目的をそろえた42課題 | 最良の一回生成は59.5%、54.8%、42.9%。実行エラーまたは誤答を返して修正させると83.3%、76.2%、66.7%へ改善［[24](#ref-24)］ | SDKごとの知識差があり、実行結果を返す修正が有効 | すべてのモデル・課題で同じ改善が出ること |
| ChatGPTによる量子プログラム修正 | Bugs4Qの再現可能なQiskit不具合38件 | 29件を修正。各条件で最大5回の生成と会話を行い、全テスト通過で正解判定［[32](#ref-32)］ | 不具合説明、期待出力、テスト結果を与えた反復修正の可能性 | 一回の生成で29件直ること、論文からの新規実装 |

以上から、**「AIが使える」ことと「AIの出力をそのまま正解と扱える」ことは別である。** 特に、QuanBench+とChatGPT修正研究は、エラーや期待出力を返し、テストを繰り返す条件で改善している。［[24](#ref-24)］［[32](#ref-32)］

### 6.2 論文から実験までを扱った事例

量子コードの短い課題だけでなく、論文から実装・実験までを扱う新しい報告も確認した。

| 事例 | 実施内容 | 実際に起きた問題 | 証拠としての制限 |
|---|---|---|---|
| 中性原子QPUのエージェント型作業 | 論文または特許から、Pasqalの中性原子QPU実験までを3事例で実施 | 1件では不適切な観測量を選び、別の1件ではもっともらしいが誤ったハードウェア原因を説明した。両方とも分野専門家が発見［[34](#ref-34)］ | 2026年プレプリント、3事例、特定プラットフォーム |
| 量子多体系のPaper-to-Program | 論文をいったんレビュー可能な技術仕様へ変換してから、DMRGなどを実装 | DMRG校正課題では直接実装6/13に対し仕様経由16/16、別課題では直接実装0に対し仕様経由11/26。曖昧さを外に出して確認する効果を報告［[35](#ref-35)］ | 2026年の単著プレプリント。量子回路SDKではなく多体計算 |
| Quantum Vibecoding | 一人の実施者とAIエージェントが、複数論文をシミュレータ・複数実機で再現 | ビット順、ハミルトニアン係数の方式、Xゲート位置、集計済み結果の誤りが、既知解や別実行先との比較で発見された［[36](#ref-36)］［[37](#ref-37)］ | 自己公開プロジェクトの事例報告であり、査読済み比較研究ではない |

DMRGは、量子多体系の基底状態などを古典計算で近似する手法である。第2行の研究は「論文から実装する際の曖昧さ」を扱う点では参考になるが、QURI SDKの回路生成を直接評価していない。

### 6.3 AIについて現時点で言えること

**確認できたこと**

- 量子コード生成の成績は、SDK、モデル、課題、評価方法で変わる。
- Pythonが実行できるかだけでなく、回路実行、確率分布、古典後処理、期待値をテストする評価が使われている。
- 実行エラーや誤答をAIへ返す反復修正は、一回生成より高い成績を示した研究がある。
- 論文から実機までの3事例では、専門家だけが発見した科学的な誤りがあった。

**まだ確認できていないこと**

- 量子研究者がQURI SDKコード作成にAIをどの程度日常利用しているか。
- 論文、数式、図、補足資料を与えたとき、QURI SDKコードをどの程度正しく生成できるか。
- 量子化学、NISQ、Early-FTQC、FTQCで、AIの誤り方がどう違うか。
- QURI SDKの版や外部バックエンドを指定した場合に、古いAPI生成をどこまで防げるか。

## 7. 今後の検証：QURI SDKで実証すべき仮説

> **この章の要点**  
> 次の段階では、一般研究の問題がQURI SDKでも現れるかを、既知解と論文値を持つ課題で確かめる。評価の中心は速さではなく、誤りを見つけ、原因を説明し、同じ条件で再実行できることである。

### 7.1 再現実験の基本設計

少なくとも10件の公開研究を候補にし、次の領域が偏らないように選ぶ。

- 量子化学・VQE。
- QAOAなどのNISQ変分アルゴリズム。
- 量子物理の時間発展・期待値計算。
- Early-FTQC・FTQC向けの回路と資源見積もり。
- 外部SDKまたは複数バックエンドを使う例。

各課題は、次の順で実行する。

1. **再現対象を固定する**：論文の図、表、期待値、確率分布など、再現する主張を一つ以上指定する。
2. **条件を記録する**：論文の式、初期状態、パラメータ、依存版、回路変換、ショット数、実行先を記録する。
3. **人手で基準実装を作る**：小規模な既知解、厳密計算、著者コードのいずれかと照合する。
4. **AIを使った実装を別に作る**：同じ資料と同じ判定基準を使い、一回生成と実行結果を返す再修正を分ける。
5. **工程ごとに比較する**：入力、状態、演算子、回路、変換後回路、測定、後処理、最終値を順に確認する。
6. **新しい環境で再実行する**：記録だけを使い、別環境または新しい環境から同じ結果へ到達できるか確認する。

### 7.2 成否の判定

実行時間の短さを主判定にしない。課題ごとに、次の五点を判定する。

| 判定 | 合格条件 |
|---|---|
| 実行可能性 | 必要な依存関係と入力がそろい、例外なく完了する |
| 数学・物理上の正しさ | 既知解、保存則、期待する状態、厳密計算のいずれかと一致する |
| 論文との一致 | 対象にした図・表・数値を、事前に決めた許容差内で再現する |
| 原因の説明可能性 | 不一致を、入力、古典処理、回路、変換、測定、雑音、実行環境のどこかへ絞れる |
| 再実行可能性 | 記録した条件だけで、別の実行者または新規環境が同じ判定へ到達できる |

### 7.3 仮説ごとの確認方法

| 仮説 | 仕込む、または観察する違い | 確認するもの |
|---|---|---|
| 仮説1 環境・版 | QURI SDK、Python、外部SDKの版を変える | ライブラリ読込、API、依存解決、結果の変化 |
| 仮説2 古典処理 | パラメータ順、配列形状、最適化停止条件、集計式を変える | セルが成功したまま最終値が誤るか |
| 仮説3 初期状態・回路 | 初期状態、制御・標的、回転角、量子ビット番号を変える | 状態、期待値、測定分布のどこで差が最初に出るか |
| 仮説4 アンコンピューティング | 補助量子ビットを戻す場合と戻さない場合を比べる | 補助量子ビットとのもつれ、干渉、最終分布 |
| 仮説5 回路変換 | 変換器、最適化段階、量子ビット配置を変える | 意味の変化と、並びだけの変化を区別できるか |
| 仮説6 測定・雑音 | 理想状態、有限ショット、雑音モデル、実機を分ける | 統計誤差、系統的なずれ、コード不具合を区別できるか |
| 仮説7 論文再現 | 著者コード、論文だけ、補足資料込みを比べる | 何の情報がないと同じ結果へ到達できないか |
| 仮説8 AI実装 | 人手、一回生成、実行結果を返す再修正を比べる | 誤りの種類、テストで発見できた箇所、専門家確認が必要な箇所 |

### 7.4 実験記録の最小項目

- 論文と再現対象の図・表・数値。
- 使用した式と、その出典ページ。
- QURI SDK、Python、外部ライブラリの版。
- 初期状態、演算子、回路、パラメータ。
- トランスパイラ、量子ビット配置、実行先。
- ショット数、乱数、雑音・誤り軽減条件。
- 工程ごとの中間結果と最終結果。
- 期待値との差、許容差、合否。
- 発生した問題、原因、修正内容、修正後の再実行結果。
- AIを使った場合は、入力資料、指示、生成物、AIへ返したエラー、採用しなかった出力。

## 8. 結論

> **この章の要点**  
> QURI SDKとの連携で先に解くべき問いは「何を表示するか」ではなく、「どの工程で正しさを失い、現在どう確かめているか」である。

### 8.1 文献と公開記録から確認できたこと

1. **量子プログラムは、Pythonが正常終了しても誤結果になり得る。** 初期状態、パラメータ、回路設計、ビット順、変換、後処理が具体的な原因として報告されている。［[7](#ref-7)］［[17](#ref-17)］［[18](#ref-18)］
2. **不具合は量子回路だけに閉じない。** 古典コード、依存関係、SDK間の境界、シミュレータ、実機、結果解釈まで調査対象になる。［[7](#ref-7)］［[20](#ref-20)］［[25](#ref-25)］
3. **回路の目視は使われているが、大規模回路では限界がある。** 回路図の有無と、計算の正しさを確認できることは同じではない。［[7](#ref-7)］
4. **論文再現には、コード以外の条件が必要である。** 依存版、入力、変換、測定、実行先が欠けると、同じ計算へ到達できない。［[12](#ref-12)］［[13](#ref-13)］［[14](#ref-14)］
5. **AIは生成と修正に利用できるが、出力を無条件に正解とは扱えない。** 実行テスト、既知解、複数実行先、専門家レビューが誤りの発見に使われている。［[22](#ref-22)］［[24](#ref-24)］［[31](#ref-31)］［[34](#ref-34)］

### 8.2 QURI SDKについての現時点の判断

QURI SDKは、回路・状態・演算子、変分計算、量子化学、回路変換、Sampler・Estimator、外部SDK連携を一続きで扱う。この構造には、一般研究で報告された問題と照合すべき箇所がある。

一方、QURI SDKについて直接確認できたのは、公式リリースの修正、版を固定した公式課題環境、周辺連携のIssue、個人の導入事例などに限られる。**一般研究の問題がQURI SDKでもどの程度起きるかは、まだ事実として確定していない。**

### 8.3 次に行うこと

次の段階では、第7章の方法で10件程度の再現実験を行う。各工程の入力と中間結果を残し、どこで誤りが入り、どの確認で発見でき、修正後に論文値または既知解へ到達できたかを記録する。その結果を得てから、Qni Notebookで扱う問題と必要な支援を定義する。

## 付録A. 用語集

> **この付録の役割**  
> 本文中の専門用語を、QURI SDKを初めて使う読者にも追える範囲で説明する。

| 用語 | 本資料での意味 |
|---|---|
| QURI Parts | 回路、量子状態、演算子、Sampler、Estimator、回路変換などを扱うQURI SDKの基礎ライブラリ |
| QURI Algo | 主にEarly-FTQC・FTQC向けの量子アルゴリズムと部品を扱うライブラリ。NISQ向け部品はQURI Parts側にも含まれる |
| QURI VM | デバイス条件を含むシミュレーション、実行、資源見積もりを扱うライブラリ |
| SDK | Software Development Kit。特定の環境でプログラムを作るためのライブラリ、ツール、文書のまとまり |
| Qiskit / Cirq / PennyLane | Pythonから量子回路の作成や実行を行うための代表的な量子SDK |
| Qulacs | 量子回路を古典コンピュータ上で計算する量子回路シミュレータ |
| PySCF / OpenFermion | 分子の電子状態計算や、電子の演算子を量子ビット上の演算へ変換する際に使われるライブラリ |
| メタパッケージ | 関連する複数のライブラリを、互換する組み合わせでまとめて導入するためのパッケージ |
| API | ライブラリが公開する関数やクラスの使い方。更新で名称や引数が変わる場合がある |
| 依存関係 | あるライブラリを動かすために必要な別ライブラリと、その版の組み合わせ |
| 後方互換性 | 新しい版でも、古い版向けのコードやデータを引き続き扱える性質 |
| QPU | Quantum Processing Unit。量子回路を実行する処理装置 |
| NISQ | 誤り訂正が十分でない現在型の量子計算機。雑音があり、回路の大きさや深さに制約がある |
| Early-FTQC | 大規模な完全誤り耐性計算より前の段階を想定した、初期の誤り耐性量子計算 |
| FTQC | Fault-Tolerant Quantum Computing。誤り訂正を使いながら計算を続ける量子計算 |
| 量子状態 | 量子ビットが持つ振幅と位相を含む計算状態 |
| 状態ベクトル | 量子状態を複素数の配列で表したもの。量子ビット数に対して配列長が指数的に増える |
| 演算子 | 量子状態へ作用する数学的な操作。観測量やハミルトニアンの表現にも使う |
| 観測量 | 実験や計算で値を求める物理量。エネルギー、磁化など |
| ハミルトニアン | 系のエネルギーと時間発展を表す演算子 |
| 試行回路（Ansatz） | 変分計算で使う、調整可能なパラメータを持つ試行回路・試行状態 |
| 変分アルゴリズム | 量子回路のパラメータを古典計算で更新しながら、目的値を改善する反復型の計算方法 |
| Optimizer | 変分アルゴリズムで、目的値を基に次のパラメータを決める古典側の最適化処理 |
| Sampler | 回路を繰り返し実行し、測定されたビット列と回数を返す仕組み |
| Estimator | 量子状態と演算子から期待値を計算・推定する仕組み |
| バックエンド | 回路を実行するシミュレータや実機サービス。SDKと実行先をつなぐ部分も含む |
| 期待値 | 同じ測定を多数回行ったときに得られる値の平均に相当する量 |
| ショット | 同じ量子回路を実行して測定する1回。有限ショットでは統計的な揺れが残る |
| 標準誤差 | 有限個の標本から求めた平均値が、どの程度揺れ得るかを表す量 |
| 校正情報 | 実機のゲート誤差や読出し誤差など、その時点の装置状態を測って記録した情報 |
| 誤り軽減 | 誤り訂正を全面的に行わず、測定や追加計算によって雑音の影響を小さくする処理 |
| トランスパイラ | 回路の意味を保つことを目標に、実行先のゲートや量子ビット接続へ合わせて回路を変換する処理 |
| 量子ビット配置 | 論理上の量子ビットを、実機上のどの量子ビットへ割り当てるかという対応 |
| リトルエンディアン | 複数ビットの表示で、番号の小さいビットを右側へ置く表記規則 |
| CXゲート | 一方の量子ビットが1のとき、もう一方を反転させる二量子ビットゲート。CNOTとも呼ぶ |
| SWAPゲート | 二つの量子ビットの状態を入れ替えるゲート |
| 忠実度 | 二つの量子状態がどの程度近いかを表す値。通常は1に近いほど似ている |
| 補助量子ビット | 中間計算のため一時的に使う量子ビット。ancillaとも呼ぶ |
| アンコンピューティング | 中間計算の逆操作を行い、補助量子ビットを元の状態へ戻すこと |
| 量子もつれ | 複数量子ビットの状態を、各量子ビットの独立した状態として分けて表せない関係 |
| 量子干渉 | 量子状態の振幅が強め合ったり打ち消し合ったりすること |
| サイレントな誤結果 | 例外やクラッシュを出さず、もっともらしいが誤った結果を返すこと |
| 基底関数 | 量子化学で分子軌道を表すために組み合わせる数学的な関数 |
| 活性空間 | 量子化学計算で、詳しく扱う電子と軌道を選んだ範囲 |
| フェルミオン―量子ビット写像 | 電子の生成・消滅演算子を、量子ビット上の演算へ変換する規則。Jordan–Wigner写像などがある |
| Qsub | QURI PartsでFTQC向けの構造化された量子プログラムを記述する仕組み |
| LLM | Large Language Model。文章やコードを生成する大規模言語モデル |
| 推論モデル | 複数段階の推論を伴う問題に向けて設計された言語モデル。本資料ではQCoder Benchmarkが分類したモデル区分を指す |
| DMRG | Density Matrix Renormalization Group。量子多体系の低エネルギー状態を古典計算で近似する手法 |
