# Qni Notebookに追加し得る機能候補集

## サマリー

基礎調査報告書では、QURI SDKを使う作業について、環境構築からPython処理、量子回路、回路変換、実行、結果解釈、再現までに**16種類の問題**を整理した。本資料は、その各問題に対してQni Notebookが取り得る解決策を、実装可能性で絞らず列挙したものである。問題番号は [Qni NotebookとQURI SDK連携のためのワークフロー分析](./qni-notebook-ai-research-workflow-analysis.md) と共通である。

候補は「回路を見やすく描く」だけには収まらない。必要になり得るのは、**動く前に間違いを防ぐ機能、動いた後に正しさを確かめる機能、違いの発生箇所を探す機能、実験条件を残す機能、AIの出力を検査する機能**である。本資料では、これらを含む130件の候補を挙げた。

ただし、文献が裏づけるのは主として「問題が存在すること」や「既存の検査方法があること」である。**130件すべてがQni Notebook利用者に必要だと実証されたわけではない。** 各候補は、基礎調査で確認した問題と既存研究・既存ツールから組み立てた解決仮説であり、採用判断にはQURI SDKを使った再現実験と利用者調査が必要である。

### この資料で数えたもの

| 項目 | 内容 |
|---|---|
| 基礎となる問題 | 問題01〜問題16。番号は基礎調査報告書と共通 |
| 機能候補 | F001〜F130 |
| 現行Qniとの関係 | **基盤拡張**＝現行機能を広げる、**新規**＝新しい画面・処理、**研究構想**＝研究段階の方法も含む |
| 根拠の読み方 | 文献・公式資料に同種の方法がある場合は参考文献番号を記載。Qni向けの画面や組合せは本資料の提案 |
| 対象外 | 工数、実装難易度、優先順位、事業価値の確定 |

## 1. 基礎調査で確認した問題

| 番号 | 問題 | 画面上ではどう見えるか |
|---|---|---|
| 問題01 | Python以外も含む依存関係の不足 | QURI SDKやシミュレータを読み込む前後で導入が止まる |
| 問題02 | SDK更新、API廃止、依存版の衝突 | 以前動いたNotebookが更新後に動かない |
| 問題03 | 論文再現に必要なコード・データ・環境・実機条件の不足 | 論文を読めても同じ実験を開始できない |
| 問題04 | Pythonの配列、設定、最適化、集計など古典側の誤り | 回路は正しくても最終値やグラフが誤る |
| 問題05 | 初期状態、配列形状、パラメータ順の取り違え | セルは成功するが別の状態・条件を計算している |
| 問題06 | ゲート、制御・標的、回転角、量子ビット番号の誤り | 回路もシミュレーションも作れるが別の処理になる |
| 問題07 | ビット列の表示順・読み順の取り違え | `01`と`10`などを逆の意味に読む |
| 問題08 | 補助量子ビットを元へ戻し忘れる | 例外は出ないが不要なもつれが残り、後の出力が変わる |
| 問題09 | 回路変換が計算の意味を変える | 最適化後も実行はできるが結果が変わる |
| 問題10 | 回路変換で量子ビットの配置・並びが変わる | 状態配列が違って見えるが、並びの差か意味の差か分からない |
| 問題11 | 有限ショットによる統計的な揺れ | 同じ回路でも実行ごとに値が少し変わる |
| 問題12 | コード不具合、統計揺れ、実機雑音の切り分け | 参照値との差が何に由来するか分からない |
| 問題13 | シミュレータや実行基盤自身の不具合 | 正しいコードでも、もっともらしい誤結果が返る |
| 問題14 | 回路が大きくなり目視確認できない | ゲートの欠落や位置違いを回路図から探しきれない |
| 問題15 | 外部SDK・ライブラリ間の干渉 | 単独では動く組合せが同じPythonプロセスでは例外を起こす |
| 問題16 | 文書、理論説明、使用例、出力解釈の不足 | APIは見つかるが、何を設定し何を読めばよいか判断できない |

基礎調査では、これらのうちQURI SDKで直接確認した個別事例と、他SDKの研究からQURI SDKにも起こり得るとした仮説を分けている。本資料も、発生頻度を確認していない問題を「QURIで多発している」とは記述しない。

### 4.4 量子状態・回路の正しさ

Pythonが例外なく終わっても、初期状態、回転角、制御・標的、観測量が違えば別の計算になる。Qniの段階表示を土台に、単なる表示から「何が期待と違うか」の検査へ広げる候補である。量子状態の完全表示は量子ビット数に対して指数的に大きくなるため、部分表示も必要になる。［[B01](#ref-b01)］［[R12](#ref-r12)］

### 5.1 一例：「VQEの値が論文と違う」とき

1. F012で、比較対象を「論文図3、結合長0.74 Åのエネルギー」と固定する。

## 6. 採用候補を絞るために測ること

この資料は優先順位を決めない。次の再現実験では、各機能候補について少なくとも以下を測り、問題が実際に起きるか、その機能で見つけられるかを確かめる。

| 観点 | 確認する問い | 記録する値 |
|---|---|---|
| 問題の発生 | QURI SDKを使う10件程度の課題で、その問題は実際に起きたか | 問題番号、工程、再現手順、発生件数 |
| 検出 | 機能が誤りを見つけたか | 検出できた誤り、見逃した誤り |
| 誤警告 | 正しい処理を誤りと判定しなかったか | false positive、未判定、理由 |
| 原因特定 | 利用者が修正すべきセル・変数・回路区間まで絞れたか | 特定できた範囲、必要だった追加確認 |
| 正しさ | 修正後に既知解、保存則、論文値へ到達したか | 期待値との差、許容差、統計判定 |
| 再現 | 空環境・別実行者でも同じ判定になったか | 環境、入力、成功／失敗、差分 |
| 理解 | 専門用語だけでなく、利用者が次に何を直すか判断できたか | 観察記録、インタビュー、誤解した箇所 |
| 作業量 | 正しさを落とさず確認負荷が減ったか | 操作数、手作業の比較数、所要時間 |

所要時間は評価項目に含めるが、主判定は**速さではなく、誤りを見つけ、原因を説明し、正しい結果を再現できたか**とする。

### 6.1 文献から直接は決められないこと

- QURI SDK利用者に16問題がどの頻度で起きるか。
- どの問題が研究停止や誤った結論につながりやすいか。
- 130候補のうち、利用者がNotebook内で本当に使うものはどれか。
- 自動検査の許容できる誤警告率と計算費用。
- AIへ渡してよい論文・実験データの範囲。
- 小規模な状態ベクトル確認から大規模回路・実機へ、どの表示を引き継ぐべきか。

これらは将来の実験・利用者調査で埋めるべき空欄であり、本資料では事実として断定しない。

## 7. 用語集

| 用語 | 本資料での意味 |
|---|---|
| アサーション | プログラムの途中または最後で満たすべき条件。「ancillaが0」「期待値が範囲内」など |
| global phase | 量子状態全体に共通して掛かる位相。観測結果を変えないため、状態比較では無視する場合がある |
| 縮約密度行列 | 全量子ビットではなく、選んだ一部の量子ビットの状態を表す行列 |
| 性質ベーステスト | 一つの正解値ではなく、常に成り立つ性質から入力と検査を作る方法 |
| メタモルフィックテスト | 正解値が分からなくても、意味を保つ変換の前後で成り立つ関係を検査する方法 |
| ミューテーションテスト | 人工的な小さな誤りを入れ、既存テストがその誤りを検出できるか確かめる方法 |
| 回路等価性検査 | 二つの回路が、許容する違いを除いて同じ量子操作を行うか確認する方法 |
| トランスパイル | 回路を実行先のゲート集合・接続へ合わせ、変換・最適化する処理 |
| routing | 接続していない物理量子ビット間の操作を実現するため、SWAPなどを挿入する工程 |
| ancilla | 中間計算に一時利用する補助量子ビット |
| アンコンピューティング | 一時計算の逆処理を行い、補助量子ビットを元の状態へ戻すこと |
| raw counts | 並べ替え、正規化、誤り軽減などを行う前の、測定ビット列ごとの回数 |
| 信頼区間 | 推定値が含まれると考える範囲を、指定した信頼水準で示したもの |
| 効果量 | 差があるかだけでなく、差がどれほど大きいかを表す量 |
| Hamiltonian | 系のエネルギーなどを表す演算子。VQEでは期待値を小さくする対象になる |
| 活性空間 | 量子化学計算で詳しく扱う電子と軌道を選んだ範囲 |
| Ansatz | 変分計算でパラメータを調整する試行回路・試行状態 |
| Pauli項 | Hamiltonianなどを、I・X・Y・Zの積と係数で分解した各項 |
| tapering | 対称性を使い、必要な量子ビット数を削減する方法 |
| chemical accuracy | 量子化学でしばしば目安に使われるエネルギー誤差の範囲。採用値と単位は実験ごとに明記する |
| Qsub | QURI Partsで大きなFTQC回路をサブルーチンとして構造化する仕組み |
| QURI VM | アーキテクチャ・デバイス条件を抽象化し、sampling、estimation、analysisを行う仕組み |
| magic-state factory | FTQCで非Clifford操作に必要な高品質状態を作る設備・処理。資源見積もりの大きな要素になり得る |
| API drift | SDK更新でAPIが変わり、生成コードや既存コードが対象版と合わなくなること |
| 来歴（provenance） | データや結果が、どの入力、処理、版、実行から作られたかという記録 |

- **査読済み研究**は、問題や手法の存在を支える主な根拠とした。ただし、多くはQiskit、Q#などを対象とし、QURI SDKだけの効果測定ではない。
- **QURI SDK、IBM、Microsoft、PennyLaneの公式資料**は、現在提供されるAPIや作業単位を確認するために用いた。利用者が実際に困る頻度は公式資料からは分からない。
- **2025〜2026年のプレプリント**は、AI、Notebook再現性、シミュレータ、実機変動に関する直近の結果として採用した。査読・改訂で結論や数値が変わる可能性がある。
- **GitHubのリポジトリ・Issue**は、実装や個別事例の確認に限って用いた。一件の事例から一般的な発生率を推定していない。
- 表の「根拠」は、同種の問題・検査方法・データ記録方法が存在することを示す。**その文献がQni Notebook向けのUIや130候補の採用を推奨したという意味ではない。**
